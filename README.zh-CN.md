### 原理与公式（第一版）

#### 核心原理

**个人模式改变输入内容；团队 API 模式研究计算复用。**
这是两种不同的机制，必须分别测量。

个人模式在保留任务指令和所需材料的同时，删除受支持的规则识别为不必要的
内容或 JSON 空白，从而减少发送给模型的输入。当前实现使用确定性规则，
并不是一个已经训练好、能够理解任意任务的通用压缩器。没有适用的受支持
转换时，会保留原文；提出的候选仍然需要用户审核。

团队 API 模式研究供应商缓存能否复用重复的稳定前缀，以及 keepalive
（保活）是否值得其额外成本。缓存命中可能减少重复计算及其相关费用，
但不意味着发送的 token 数量减少。这项功能属于桌面项目，不在公开网站中运行。

#### 1. 本地输入减少

设 `x` 为原始输入，`x′` 为候选，`T` 为同一个本地 tokenizer（分词器）。
两种输入必须采用相同的计数规则，并且原文 token 数必须为正：

$$
\Delta T = T(x)-T(x'), \qquad
r_{\mathrm{input}}=1-\frac{T(x')}{T(x)}
$$

`ΔT` 是本地输入减少的 token 数；`100 × r_input` 是页面显示的输入减少百分比。
对于本文记录的英文 JSON 示例，`T(x)=34`、`T(x′)=25`，因此实测本地输入减少为
`9 tokens ≈ 26.47%`——这不是额度节省的测量结果。

#### 2. 任务级优化目标

研究目标是在将质量损失控制在事先声明的容许范围内的同时，减少完成任务所消耗的总资源：

$$
\min_s \mathbb{E}[U(s)] \quad
\text{subject to}\quad Q_0-Q_s\leq\varepsilon
$$

这里，`s` 是一种策略，`U(s)` 是按照同一种、一致定义的指标统计的总消耗，
包括优化器模型调用和每一次任务尝试。`Q_0` 是基线质量分数，`Q_s` 是使用同一套
独立定义的评分标准评估出的策略质量分数，`ε` 是允许的质量损失。
这是一个研究目标，不表示引擎已经计算出了全局最优解。规则检查不能替代
对模型输出的评估。

#### 3. 简化缓存经济模型

对于团队 API 模式，一个简化的预期净收益模型为：

$$
G=p_{\mathrm{reuse}}(h_s-h_0)D-K
$$

`p_reuse` 是未来复用的概率；`h_s - h_0` 是在发生复用的条件下，策略带来的
缓存命中概率提升；`D` 是一次复用由未命中变成命中时可避免的费用；`K` 包括
额外的保活、写入和存储成本。只有当假设成立且 `G > 0` 时，这个简化模型才
支持可能实现净节省的判断。公式本身不是实测结果。

#### 4. 完整任务的实测对照

实际对照必须计入两组的完整消耗，而不只是输入长度：

$$
r_{\mathrm{task}}=1-\frac{U_B}{U_A}, \qquad
\Delta Q=Q_B-Q_A
$$

`A` 是原始任务组，`B` 是优化任务组。消耗包含失败尝试和重试；基线必须可获得且为正。
`ΔQ` 是优化组质量减去基线质量；负值意味着质量更低。两组必须使用相同的
消耗指标和质量评分标准。本地 token 减少、完整任务总消耗、API 费用和订阅额度
是各自独立的指标。当前没有实现通用的 token 到订阅额度换算。

### 代码如何实现这些逻辑

```text
用户输入
  -> app.js：界面状态、请求 ID、审核和复制
  -> worker.mjs：本地 tokenizer + Python/WASM 运行时
  -> 桥接层（打包在 worker 中）：JS/Python 消息、最新方案
  -> cachescope/engine.py：保存原文、分派、校验、封存
       1. record_selector.py：精确匹配受支持的 id-to-code 查询
       2. code_context_optimizer.py：有界 Python 依赖选择
       3. context_optimizer.py：显式引用 / 完全重复的文本
       4. prompt_compressor.py -> structural_compactor.py：JSON 空白
     采用第一个适用的策略，并不是始终将四种转换串联执行。
  -> 候选与计数
  -> 用户审核 -> Engine.confirm() -> 复制到用户使用的助手
```

| 模块 | 职责 | 重要边界 |
| --- | --- | --- |
| `cachescope/engine.py` | 选择策略、保留原始基线、校验和确认 | 不调用目标模型，也不验证其回答 |
| `cachescope/config.py` | 输入与确认限制 | 默认 50,000 字符，900 秒确认窗口 |
| `cachescope/models.py` | 输入快照、计数和哈希 | 哈希不是语义质量的证据 |
| `cachescope/optimizers/record_selector.py` | 在精确的查询约定下选择一条记录 | 不是通用数据库查询引擎 |
| `cachescope/optimizers/code_context_optimizer.py` | 解析受限的 Python，并保留具名依赖 | 不执行提交的代码，也不支持任意代码仓库 |
| `cachescope/optimizers/context_optimizer.py` | 选择带标签的上下文，或删除完全重复的文本 | 不是通用摘要或语义去重 |
| `cachescope/optimizers/retention_guard.py` | 校验声明的删除区间和保留文本 | 不能证明被省略的事实无关紧要 |
| `desktop/structural_compactor.py` | 压紧受支持的 JSON，并还原编辑 | 还原需要已保存的补丁 |
| 开发目录中的 `web/app.js`、`web/bridge.mjs`、`web/worker.mjs` | UI、Python 桥接层和浏览器执行 | 公开构建产物将桥接层/worker 打包，并导出选定的 Python 源码 |

在这个公开仓库中，上述 Python 模块打包在
[`python-sources.json`](python-sources.json) 中，而不是以独立目录的形式存在。
浏览器文件位于仓库根目录：[`app.js`](app.js)、[`worker.mjs`](worker.mjs)、
[`index.html`](index.html) 和 [`styles.css`](styles.css)。
完整的私有源码路径用于说明开发模块，并不表示整个桌面端源码都已在此公开。

## 用户怎么使用

### 从这里开始：无需安装，也不需要 API 密钥

1. 打开 [CacheScope Web](https://thisisyk.github.io/cachescope-web/)，在右上角选择 English 或中文。
2. 阅读实验性使用说明，勾选同意框，点击**启动本地引擎 / Start local engine**。首次加载会下载运行时和 tokenizer；请等待初始化完成后再预览。
3. 保持在**个人精简 / Personal** 模式。选择你计划使用的平台，然后将准备发送的任务和上下文粘贴到**你的任务 / Your task** 中。你也可以先点击**试用示例 / Try an example**。平台选择仅用于信息展示，不会连接账户。
4. 点击**检查并预览 / Check & preview**。将原文与**候选内容 / Candidate** 对照，并查看**本次结果 / This result** 下的本地 token 计数。
5. 检查数字、名称、否定表达、格式要求和所有任务指令是否仍然正确。确认满意后，勾选**我已核对重要事实与要求 / I reviewed the important facts and requirements**，再点击**确认并复制 / Confirm & copy**。
6. 将复制的文本粘贴到 ChatGPT、Claude、Codex 或你偏好的助手中，由你自己发送。CacheScope 不会发送消息，也不会编辑其他应用的输入框。
7. 你还可以点击**下载结果（不含原文）/ Download result (no prompt text)**，保存本地测量报告。这不是订阅节省的实测报告。

中文快速流程：打开网页 → 选择语言 → 阅读并同意说明 → 启动本地引擎 →
粘贴任务（或试用示例）→ 检查并预览 → 核对候选 → 勾选已核对 → 确认并复制 →
粘贴到你原来使用的聊天工具，由你自己发送。无需安装 Python，也不需要在网页填写 API Key。

### 怎么看结果

- **原文 Token / Original tokens** 和**候选 Token / Candidate tokens** 是本地 `cl100k_base` 计数，不是从你所选平台实时读取的数据。
- **本地输入减少 / Local input reduction** 衡量的是上述计数的差值，不是 API 账单或剩余订阅额度。
- 如果文本未变或减少比例为 0%，说明没有找到适用的更短候选。使用原文即可；系统不会强求非零结果。
- 如果重要信息缺失，请不要批准候选。使用原文；如果你希望帮助改进项目，可以反馈一个经过匿名化处理的示例。
- 如果你修改了输入，或审核确认已过期，请再次点击**检查并预览 / Check & preview**。如果剪贴板权限被拒绝，请按照页面指引，使用 Ctrl+C 复制选中的文本。

中文提醒：减少的是当前输入的本地估算 token，不等于平台总消耗或订阅额度同比减少。
候选不合适就用原文；没有缩短不代表必须继续删减。请先用非敏感示例体验，不要为了
获得更高比例而删除任务所必需的信息。

## 这个演示能做什么

这是 CacheScope 个人上下文精简工具的纯浏览器发行版。

打开已发布的网站，阅读说明，启动本地引擎，粘贴任务，检查预览，然后复制候选。
无需安装 Python，也不需要 API 密钥。首次加载会下载 Python/WASM 运行时和 tokenizer。

输入在浏览器 worker 内处理。这个发行版没有提示词上传端点、账户信息收集器
或 API 密钥输入框。本地 token 估算不是平台订阅节省。不受支持的任务会保留原文。

这个公开仓库只包含浏览器资源及运行它们所需的最少 Python 模块。它不公开
私有桌面项目、训练数据、客户记录、API 凭据或模型权重。

通过 AI 辅助编程（vibe coding）构建。仍处于实验阶段：请在使用前审核改动。
所选聊天平台仅用于信息展示；所有本地估算均使用 cl100k_base。
团队 API 路由需要桌面网关。

## 为什么要做这个项目

LLM 任务可能以几种不同的方式消耗不必要的资源：

1. 用户提供了重复文本，或带有不必要格式的文本。
2. 一个范围很窄的问题却附带了远超其所需的上下文。
3. 多次 API 请求重复使用稳定前缀，而其计算本可以复用。
4. 更短的提示词产生了更差的回答，导致额外澄清或重试。

前两点是个人引擎的出发点。第三点是独立的团队缓存控制器的出发点。
第四点说明，仅凭提示词长度不足以衡量成功。目标是**以更少的不必要工作，
获得可接受的任务结果**，而不是不惜任何代价地把文本缩到最短。

不应将以下机制混为一谈：

| 机制 | 改变的是什么 | 是否包含在此浏览器版本中？ | 它不能证明什么 |
| --- | --- | --- | --- |
| 结构压紧 | 适用 JSON 的表示形式 | 是，限受支持的情况 | 完整任务或订阅用量更低 |
| 特定任务的上下文选择 | 哪些源材料会送达模型 | 是，范围有限 | 普遍的语义等价性 |
| 自由形式的模型改写 | 模型生成的自然语言表述 | 否 | 更短的措辞保留了每一项要求 |
| 供应商前缀缓存 | 供应商计算的复用 | 否；属于桌面/API 工作 | 发送的 token 更少 |
| 保活（keepalive） | 为维持可复用上下文而发出的额外请求 | 否；属于自愿启用的桌面功能 | 额外支出能够收回成本 |
| 语义响应缓存 | 先前回答的复用 | 不属于此浏览器引擎 | 对新问题仍然正确 |
| 订阅额度观测 | 读取平台结算后的用量指标 | 否 | 存在通用的 token 到额度换算 |

CacheScope 不是新的基础模型。当前公开构建产物结合了双语界面、本地 tokenizer、
有界 Python 转换规则、预览完整性检查和显式用户批准。学习式压缩与复用预测
仍然是独立的研究方向，而不是默认具备的能力。

```text
           |

           |

           |-- 有界 Python 代码上下文选择
           |-- 有界文档/上下文选择
           `-- 结构压紧 / 保留原文
           |

```

浏览器版本是个人模式演示，而不是托管的 API 网关。平台选择器不会连接账户、
读取剩余额度或更换 tokenizer。训练适配器是另一项研究活动；当前浏览器引擎
基于规则，并不是已部署的通用压缩模型。

### 运行顺序与职责划分

1. GitHub Pages 提供静态 HTML、JavaScript、CSS、tokenizer 和 Python/WASM 文件。
2. 用户同意后，`app.js` 创建一个模块化 Web Worker，并发送初始化消息。
3. worker 启动 Pyodide，将 `python-sources.json` 加载到虚拟文件系统中，
   安装 Python 引擎，并提供 JavaScript token 计数回调。
4. 预览请求将当前文本传给 `Engine.preview()`。worker 将这项计算与 UI 线程
   隔离；它不是远程推理服务器。
5. Python 桥接层在 worker 内存中保留完整的最新方案，并向 UI 返回一个更小的展示对象。
6. 确认操作将当前草稿和批准信息发回引擎。只有方案检查通过后，才会复制确认结果。
7. 新预览会替换最新方案。这个发行版没有浏览器端历史实验数据库，也没有实时订阅账户连接。

桌面端和浏览器端复用同一个 Python 核心，以减少行为差异。这并不意味着它们的
外围能力完全相同：桌面进程可以运行网关或实验；静态网站则不能。

## 个人模式原理与公式

设 `x` 为原始任务，`x'` 为提出的候选，`T` 为应用于两者的同一个本地 tokenizer。
本地输入减少量为：

```text
saved_input_tokens = T(x) - T(x')
input_reduction = 1 - T(x') / T(x)       when T(x) > 0
input_reduction_percent = 100 × input_reduction
```

例如，假设将 1,000 token 的输入减少到 750 token，本地输入就减少了 25%。
这并不能证明完整任务总用量、API 费用或订阅额度消耗也降低了 25%。

研究目标可以表述为：

```text
minimize T(x')
subject to task-relevant information and constraints being retained
and measured output-quality loss staying within an agreed tolerance
```

即：最小化 `T(x')`，同时保留与任务相关的信息和约束，并将实测输出质量损失
保持在约定的容许范围内。

这是一个目标，而不是由完美的语义判断器实现的保证。
当前引擎识别受支持的结构，并使用有界规则：

1. 在任何转换之前，保存原文及其 token 计数。
2. 先尝试受支持的记录选择，再尝试代码上下文和文档上下文，
   在前面的策略均不适用时进行结构压紧。
3. 执行该策略的检查；内容保护检查覆盖涉及数字、否定表达、实体和任务约束
   的受支持情况，但覆盖范围有限。
4. 利用编辑记录检查可逆性，并保留原始基线。
5. 返回候选供用户审核；不受支持时则保留原文。
6. 将确认操作绑定到精确的预览和原文。预览若已改变或过期，就必须重新生成；
   不会自动批准。

引擎不会穷举搜索所有可能的改写。对于明确的单条记录查询，选择记录 17
可能是合适的；但对于需要比较所有记录的任务，就不合适。在格式无关紧要时，
删除 JSON 空白可能是合适的；但在要求保留精确文本时，就不合适。

可逆性意味着编辑记录能够还原原文。它**不能**证明下游模型会产生相同的回答。
人工审核和输出评估仍然必要。普通浏览器预览不会发起额外的 LLM 请求。

## 策略约定与拒绝边界

### 1. 精确的单条记录选择

`record_selector.py` 识别特定的英文和中文 `id -> code` 查询指令。
根 JSON 对象必须仅包含 `records`；ID 必须是唯一的字符串；必须恰有一行匹配；
所选 `code` 必须是字符串。提示词必须符合受支持的指令和单个 JSON 围栏代码块结构。

选择器保留匹配的记录，并压紧该 JSON。它不能推广为任意数据库查询。
重复 ID、多个目标、无法识别的措辞、比较、聚合或额外指令都会阻止采用
此策略。不过，其他安全的回退方案仍可能适用。

被删除的记录确实不再包含于候选中。能够通过内存中的编辑记录恢复它们，
并不意味着候选本身是无损的。

### 2. 有界 Python 依赖选择

`code_context_optimizer.py` 使用 `ast` 解析一个围栏代码块中的 Python 模块；
它不会执行提交的代码。它可以保留明确指定的函数及静态具名依赖，或者保留
受支持的打印表达式及其依赖，同时删除无关定义。

允许的子集刻意保持得很小：没有装饰器的函数，其中仅包含受限表达式、局部赋值
和条件分支，之后可以有一个顶层 print。导入、类、默认参数、注解、属性访问、
动态调用、循环及其他不受支持的结构都会被此选择器拒绝。解析器将分析限制在
4,000 个 AST 节点和引擎的文本上限之内。这不是通用的代码仓库切片器，
也不是对任意 Python 代码纯粹性的证明。

### 3. 显式引用选择与完全重复内容删除

`context_optimizer.py` 包含两类有明确边界的功能：

- **引用选择：**问题明确指定一个带标签的来源，标记具有起止边界，且所选正文
  有查询词匹配依据。受支持的标记形式包括
  `<reference name="Label">...</reference>`、`[Reference: Label]...[/Reference]`
  和 `BEGIN REFERENCE: Label...END REFERENCE`。
- **重复删除：**删除受支持位置中完全重复的文本段落或句子，保留第一次出现的版本。
  不会假设相似但不完全相同的段落可以互换。

交叉引用或全局规则的线索、多个目标、比较或计数任务、受保护的引文以及代码，
都可能使这些转换不适用。即使文字完全相同，重复也可能表达强调或篇章结构，
因此精确匹配并不能消除审核的必要性。

### 4. JSON 结构压紧

`prompt_compressor.py` 将处理委托给 `desktop/structural_compactor.py`。
这不是神经网络压缩器：它在保留受支持的词法内容的同时，删除显式 JSON 围栏
代码块中允许删除的空白。要求保留原始格式或其他受保护的精确文本行为的指令，
可能阻止此次编辑。这是一种回退方式，不保证每一个包含 JSON 的提示词都会缩短。

### 5. 保留检查：范围有限的不变量，而非全知判断器

对于声明的删除区间 `D`，引用/去重保护检查验证：

```text
candidate = concatenate(original segments outside D)
restore(candidate, original edit patches) = original
protected spans do not intersect D
```

它还检查删除边界、受支持的删除类型，以及重复项是否存在精确保留的对应内容。
在这条上下文处理路径中，最多允许声明 128 处删除编辑。Python 代码路径有自己的
保护检查和依赖检查。记录选择则验证其范围很窄的 JSON/查询约定及还原结果；
并不是每一种策略都运行同样的保护检查。

数字、否定表达、实体 token 和约束检查，是将**保留材料**与候选进行比较。
被删除的来源可能包含不再出现的数字或实体。`global_inventory_unchanged`
与限定范围内的保留检查是不同概念。实体检查使用词法模式，包括大写开头的 token
和中日韩字符连续片段，而不是训练过的命名实体识别器。这些检查不能独立证明
每一次删除在语义上都无关紧要。

### 分派与回退语义

```text
保存原文快照
尝试精确记录选择
若不适用：尝试有界代码选择
若不适用：尝试有界文档/上下文选择
若仍不适用：尝试结构压紧 / 保留原文不变
校验适用的保护检查、基线统计和还原结果
封存提案；等待显式确认
```

这是一个有顺序的分派器，而不是给所有转换评分并选择全局最优解的搜索过程。
更短的输出也必须满足其策略的适用规则。不受支持的范围通常会回退到原文或
限制更严的转换；格式错误的输入、无效的计数器或完整性检查失败也可能触发错误。
发生此类错误后，不应复制任何候选。

## 预览状态与数据约定

### UI 生命周期

```text
尚未初始化 -> 同意 -> 加载中 -> 就绪
就绪 + 输入 -> 检查中 -> 未改动的原文 或 提议的候选文本
提议的候选文本 + 审阅 -> 确认 -> 复制
输入已编辑 / 方案已过期 -> 失效 -> 重新预览
失败 -> 显示错误；不要将操作视为成功
```

默认策略最多允许 50,000 个字符，确认有效期为 900 秒。对于某些 Unicode
字符，浏览器文本字段与 Python 字符串的长度计算规则可能不同；50,000 并不是
token 预算。请求处理期间，操作按钮会被禁用。系统会检查请求 ID 和捕获的
输入快照，确保旧草稿的响应不会被显示为新草稿的有效结果。

### 内部方案与导出报告的区别

| 数据 | 所在位置与用途 | 是否包含在下载的浏览器报告中？ |
| --- | --- | --- |
| 原文与候选文本 | UI 和 worker 内存；用于审阅和确认 | 否 |
| 编辑补丁与原文哈希 | 完整的 Python 方案；用于还原与完整性验证 | 否 |
| 方案 ID、创建/过期时间及审批签章 | 完整的 Python 方案；用于确认验证 | 否 |

| `local_before`、`local_after`、`local_reduction` | 本地 tokenizer 测量结果 | 是 |
| `requires_review` | 候选文本审阅标记 | 是 |
| `platform_declared` | 用户选择的标签，不是经过验证的账户/模型 | 是 |

引擎使用每个实例独有的临时 HMAC 密钥，对相关方案字段进行签章。
确认时会验证签章、完全一致的原文、审批和过期时间。
这可以防范工作流内部已过时或被修改的提议。它不是远程证明，不是模型质量的

桥接层返回部分字段；UI 会在导出前移除候选文本。
因此，下载的 `cachescope-result.json` 是本地预览报告，而不是
A/B 实验台账或详细的防护审计。不能把内部引擎中的哈希和补丁误认为

`reason` 字段会提供更具体的解释。

## 团队 API 原理：缓存与 keepalive

本节说明更广泛的桌面项目；这些控制功能不会在公开网站上运行。

稳定前缀是重复请求中保持不变的开头部分，例如共享指令和参考资料。
提供商可能复用对它进行计算的缓存结果。TTL 是提供商缓存机制下的保留时间；
它不是通用的固定值，而且一次请求不一定会刷新它。

当未缓存输入、已缓存输入和输出 token 分别定价时：

```text
C_request = (I_uncached × P_input + I_cached × P_cached + O × P_output) / 1,000,000
            + C_write + C_storage + C_other
```

价格以每百万 token 为单位。只有提供商对附加项单独计费时，这些项才适用；
不要重复计算已包含在 token 价格中的费用。缓存命中可能降低计算量或费用，
但不减少发送的 token 数。

Keepalive 会增加请求，因此需要关注的是净收益，而不是命中次数：

```text
Expected net benefit = p_reuse × (h_strategy - h_baseline) × D_reuse - K_extra
```

- `p_reuse`：在所选时间范围内，上下文再次被使用的概率。
- `h_strategy`、`h_baseline`：采用和不采用该策略时，条件缓存命中概率。
- `D_reuse`：一次复用由未命中变为命中时可避免的费用。
- `K_extra`：额外的 keepalive、写入、存储及其他策略费用。

这个简化表达式说明单次复用事件的经济性；对于重复事件，需要将其预期费用相加。
我们并不声称这些概率已在生产环境中得到准确学习。桌面的推荐路径会根据
配置的间隔和有日期标记的提供商假设，比较模拟策略。未知的保留时间不是经过
验证的证据。主动 keepalive 需要自愿启用、受到限制，而且必须与不采取任何措施
的情况进行比较。单纯的缓存命中无法证明存在净节省。

### 盈亏平衡条件与时间范围

对于简化的单次复用模型，如果 `Δh = h_strategy - h_baseline > 0`
且 `D_reuse > 0`，只有在以下条件成立时，策略的预期净收益才为正：

```text
p_reuse > K_extra / (Δh × D_reuse)
```

如果该阈值超过 1，那么假设的策略在此模型中就无法获得正收益。
如果 `Δh <= 0`，则在模型中，为 keepalive 花费费用并不带来缓存命中优势。
如果 `K_extra` 本身取决于会话何时结束，就应比较完整的预期费用，
而不是将它当作已知常量。

对于时间范围 `H` 内多个可能发生的未来请求：

```text
E[net benefit over H] = sum_j(p_j × Δh_j × D_j) - E[K_extra over H]
```

这里，`p_j` 是复用机会 `j` 发生的概率；当依赖关系不可忽略时，应使用条件模型
或联合模型。这个分解仅用于说明，不是浏览器的算法，也不是已经向用户提供服务
的训练后预测器。

以下示例数值不针对任何特定提供商：设 `p_reuse = 0.6`、`Δh = 0.7`、
`D_reuse = $0.02`、`K_extra = $0.005`。预期净收益为
`0.6 × 0.7 × 0.02 - 0.005 = $0.0034`。当 `p_reuse = 0.2` 时，它变成
`-$0.0022`。同一种 keepalive 策略可能对一种工作负载有益，却损害另一种工作负载。
这些只是算术示例，不是实测的客户节省，也不是当前 API 价格。

TTL 实验应在受控的空闲间隔之后，观察提供商报告的缓存使用情况。
在一个间隔后命中、另一个间隔后未命中，只能界定这些试验中行为的边界；
它不能证明一个通用且精确的 TTL。反复探测可能刷新缓存，干扰测量。
因此，需要独立试验、重复验证、稳定前缀，并明确区分自然保留与 keepalive 的效果。

## 评估：应如何证明改进

在相同任务、模型和评分标准下，设置原始输入组 A 与优化输入组 B。
使用未见过的任务，变换运行顺序，重复试验，并纳入失败结果，而不是只报告
成功减少输入的情况。

```text
U_arm = optimizer model usage + sum(all task attempts, including retries)
total_token_reduction = 1 - U_B / U_A
cost_reduction = 1 - C_B / C_A
time_reduction = 1 - elapsed_B / elapsed_A
quality_change = pass_rate_B - pass_rate_A
```

两组的 token 用量必须采用可比较的定义。应纳入优化耗时和所有付费的优化器调用。
普通的本地预览不会调用模型，但仍会消耗本地计算资源。计算比率需要可获取且
为正的基线；用量缺失不等于零。负的减少比例意味着增加。
在报告节省的同时，应报告质量容忍度、失败情况、样本量和不确定性。

如果存在可靠且已结算的平台额度测量数据，可以使用另一个独立指标：

```text
quota_used_arm = remaining_before - remaining_after
quota_reduction = 1 - quota_used_B / quota_used_A
```

只有在同一额度池和匹配的条件下，没有重置、购买或无关的并发活动，并且具备
足够的测量精度与结算时间，这个指标才有意义。浏览器不会收集这些测量数据。
不存在从本地 token 减少比例到订阅额度减少比例的有效通用换算方法。

### 更完整的研究方案，而不是演示声称已经取得的结果

在运行评估前，应定义任务总体、质量评分标准、允许的质量损失容忍度 `ε`、
目标模型/设置以及资源指标。将开发示例与最终评估集分开。

| 阶段 | 要控制或记录的内容 | 重要性 |
| --- | --- | --- |
| 采样 | 语言、任务类型、上下文大小、受保护内容 | 避免只测试容易缩短的案例 |
| 分组 | A 与 B 使用相同任务；随机化或平衡运行顺序 | 减少任务和顺序造成的混杂 |
| 执行 | 目标模型、工具访问权限、输出限制、重试 | 避免改变任务却声称是在优化 |
| 质量 | 独立评分标准；数值、约束和完整性 | 更短的错误答案不是没有代价的改进 |
| 核算 | 优化器开销、每次尝试、失败、缺失用量 | 防止只报告成功案例的乐观结论 |
| 分析 | 覆盖率、配对估计、不确定性、任务分组 | 揭示方法不适用的情况 |
| 决策 | 同时考量节省与约定的质量约束 | 区分有用的节省与不可接受的损失 |

在数据集层面，可使用加权汇总：

```text
aggregate_resource_reduction = 1 - sum_i(U_B,i) / sum_i(U_A,i)
quality_loss = Q_A - Q_B
candidate acceptance criterion: resource_reduction > 0 and quality_loss <= ε
```

总量之比不等于各任务百分比的平均值：它会给予资源消耗更多的任务更大权重。
如有帮助，可同时报告两者，并明确汇总方法。应分别报告不同语言/任务类别；
狭窄查找任务上的巨大收益，可能掩盖普通指令任务上的退步。

另有两个有用的诊断指标：

```text
transformation_coverage = tasks with changed candidates / all submitted tasks
measurement_coverage = pairs with valid comparable measurements / expected pairs
```

在工作负载层面的结果中，应保留未改动的任务，并单独报告缺失的测量数据。
排除失败或不可获取的配对结果，不能据此声称存在普遍节省。配对置信区间或
配对 bootstrap 可以刻画样本不确定性；这些是建议的分析方法，不是当前浏览器
报告的功能。重复试验必须考虑任务层面的依赖关系。

### 为什么输入更短，总体费用却可能更高

假设 A 只执行一次，消耗 1,000 个输入 token 和 200 个输出 token：共 1,200 个 token。
假设 B 消耗 700 个输入 token 和 200 个输出 token，但需要额外进行一次
700 输入/200 输出的尝试：共 1,800 个 token。输入长度下降了 30%，
总 token 用量却增加了 50%。实际 API 可能对这些 token 类别采用不同定价，
所以费用也必须单独评估。

如果额度显示采用舍入，显示的变化为零意味着“低于可观察精度或尚未结算”，
而不是“免费”。重置窗口和无关的账户活动会使简单的差值失效。
没有任何有限次实验能保证，在封闭的消费者平台上提供通用的逐任务额度预测。

| 浏览器内存仍保留文本 | 本地处理不等于立即擦除，也不是完整的安全保证 | 生命周期清理、威胁建模和独立安全审查 |

| 桌面构建未签名 | Windows 应用控制可能阻止安装或启动 | 在不禁用防护的前提下，进行适当签名和兼容性检查 |
| 没有生产运营承诺 | 没有 SLA、保证提供的支持、企业合规声明或完整恢复流程 | 在提供任何生产服务前，建立发布规范并开展运营/安全工作 |

## 隐私与安全使用

草稿处理在浏览器 worker 中进行。应用没有草稿上传端点，也不会收集
账户凭据或读取其他应用。获取网站仍会向托管提供商发起正常的网络请求；
本地处理并不意味着初次页面加载是离线的。
将候选文本粘贴到其他地方之前，请先审阅，尤其是涉及敏感或高风险任务时。
不要在公开的问题报告中提交秘密信息。

本地处理是一种数据流设计，不是完整的安全认证。
托管账户、浏览器、扩展和已发布的依赖仍然属于信任边界的一部分。
受入侵的环境可能访问可见文本。网站的内容安全策略将资源限制在同源范围内，
并允许引擎所需的 WebAssembly 执行；这不能替代依赖审查。
浏览器对应用文件的缓存并不保证离线运行。重新加载也不是经过认证的安全擦除程序。

尤其需要注意，清空或编辑 UI 会使预览失效，但不会立即擦除 worker 中
最新的 Python 方案。在方案被替换或 worker 被销毁之前，其中可能仍包含
原文和还原补丁。对于浏览器或操作系统中的副本，不提供安全内存擦除保证。

完整费用的 A/B 核算，以及更好的新手引导。可靠的额度观测仍是一个独立的、
依赖平台的问题，不是仅靠提示词压缩就能解决的。研究贡献和诚实的负面结果，
与成功示例一样受到欢迎。

- 验收条件：任何模拟、估计、不可获取或仅来自预览的指标，都不得被呈现为
  实测的订阅额度节省或经过验证的模型结果。

**P1 — 提高日常实用性，同时不掩盖权衡。**

- 将支持的任务结构扩展到狭窄查找模板和受限 Python 模块之外；
  解释候选文本为何被选中或拒绝。
- 仅在具备有文档记录/版本化映射的情况下，增加按模型配置 tokenizer 的功能；
  继续标明近似计数，而不是暗示能够实时访问账户。
- 扩展浏览器、移动设备、剪贴板和无障碍检查；改进初始加载、超时和重试指引，
  不绕过设备防护。
- 验收条件：在两种语言中均使用未见过的任务类别报告性能，
  并包含转换覆盖率、质量损失和总资源用量。

**P2 — 评估学习型策略与针对提供商的策略。**

- 将任何训练后的压缩器与输入不变基线和基于规则的基线进行比较，
  使用获准的数据、隔离的测试集，并纳入所有推理费用。
- 将缓存策略与不干预和固定策略进行比较；衡量净节省，
  而不是只衡量缓存命中。
- 只有在经过同意、且能够获取适当工作负载数据的情况下，才研究复用预测。
  仅凭公开训练数据，无法确定提供商的 TTL 行为。
- 验收条件：增加的复杂度能够在声明的质量容忍度下，产生可复现的样本外收益。
  否则，保留更简单的基线。

**分发与协作 — 持续进行，与算法研究分开。**

改进源代码/产物可追溯性、发布检查、桌面签名和清晰的贡献流程。
保持公开浏览器分发与私有完整源代码的区分，并记录贡献者实际上可以复现什么。
这些打包方面的变化，本身都不能证明节省声明。

中文开发顺序：先把安全边界和真实测量补完整，再扩展日常中英文任务与兼容性，
最后用严格对照实验判断训练模型、缓存预测等复杂方案是否值得加入。每一步都需要
验收依据，而不是只增加功能按钮或宣称一个节省百分比。

### 中文技术导读

本项目分成两个思路：个人模式减少任务里不必要的输入；团队模式研究重复前缀
能否复用，以及 keepalive 的额外费用是否值得。目前公开网页只运行个人模式。
核心不是一个已经训练好的通用压缩大模型，而是规则选择器、结构检查、tokenizer
和人工确认流程。它不会自动读取你的订阅额度，也不会直接操作其他软件的输入框。

个人模式的公式是 `1 - 候选 token / 原文 token`。这只是输入层面的变化；
真正评价任务效果，还要统计输出、错误重试、优化开销和质量差异。团队模式的判断
则是“未来复用概率 × 缓存命中改善 × 单次可省费用 − 保活等额外费用”。两类指标
不能混为一谈，更不能把本地 token 减少直接换算成订阅额度节省。

程序先尝试适用范围很窄的记录选择，再尝试受限的 Python 依赖选择、文档选择
或去重，最后尝试 JSON 空白精简。不适用时可以保留原文。检查保证的是声明范围内
的结构一致性，不是“所有任务都完全无损”。未来重点是扩大适用范围、增强质量检查、
做好独立评测，并欢迎其他开发者帮助验证失败案例，而不是把实验结果包装成商业保证。
